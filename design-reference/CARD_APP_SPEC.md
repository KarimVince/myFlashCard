# Training/Recipe Card Viewer — Android App Spec

## What this app does
A simple Android app that reads a JSON "card deck" file from the phone's storage
(picked via the standard Android file picker) and displays it as a swipeable
set of cards — used to follow along during training, cooking, or study, without
needing to touch the phone much.

No login, no server, no network calls in the app itself. All data lives in a
JSON file the user gets from elsewhere (e.g. generated by Claude in a chat)
and loads manually.

## Reference implementation
A working HTML/CSS/JS prototype (`card_viewer_v2.html`) already exists and
defines the exact visual design and interaction model. Treat it as the source
of truth for:
- Layout structure (top bar, card area, bottom nav)
- Color system (deck/card/block-level accent colors, computed light tints for
  table row stripes)
- Block types and how each renders
- Swipe/tap navigation behavior

Port this design into Kotlin + Jetpack Compose as faithfully as possible.

## Screens

### 1. Picker screen (initial screen)
- Centered title "Cards", short instruction text
- One button: "Load card file" → opens Android's system file picker
  (`ACTION_OPEN_DOCUMENT` or `ACTION_GET_CONTENT`, mime type `application/json`)
- On successful pick: parse the JSON, navigate to the Viewer screen
- On parse failure: show a simple error message, stay on picker screen

### 2. Viewer screen
- Top bar: deck title (left), "current / total" progress counter (right)
- Main card area: renders the current card (see "Card rendering" below)
- Tap left 25% of screen = previous card, tap right 25% = next card
- Swipe left/right also navigates (with a short slide+fade transition,
  ~160-180ms)
- Bottom bar: Prev button (left), progress dots (center), Next button (right)
- Prev/Next buttons disabled at the first/last card
- Card content scrolls vertically if it overflows the screen height

## JSON schema

```json
{
  "deckTitle": "string",
  "accentColor": "#RRGGBB (optional, deck-level fallback color)",
  "cards": [
    {
      "title": "string",
      "subtitle": "string (optional)",
      "accentColor": "#RRGGBB (optional, overrides deck color for this card's title)",
      "blocks": [ /* see block types below, rendered in array order */ ]
    }
  ]
}
```

### Block types

Every block has a `"type"` field. Most support an optional `"accentColor"`
that overrides the deck/card color for that block only.

**note** — centered, bold, colored text (no box/background). Used for goals,
tips, warnings.
```json
{ "type": "note", "text": "string", "accentColor": "#RRGGBB (optional)" }
```

**stats** — a horizontal row of equal-width stat tiles (e.g. prep time,
servings, reps).
```json
{
  "type": "stats",
  "items": [ { "label": "string", "value": "string" }, ... ]
}
```

**steps** — a list, either bulleted or numbered.
```json
{
  "type": "steps",
  "heading": "string (optional)",
  "style": "bullet | number",
  "accentColor": "#RRGGBB (optional)",
  "items": [ "string", ... ]
}
```

**table** — a 2+ column table with a colored header row and lightly tinted
alternating rows (tint = the block's accentColor blended ~78% toward white).
The first column of each row is bold and colored with the block's accent.
```json
{
  "type": "table",
  "heading": "string (optional)",
  "accentColor": "#RRGGBB (optional)",
  "columns": [ "string", ... ],
  "rows": [ [ "cell", "cell", ... ], ... ]
}
```

**text** — plain paragraph, no special styling.
```json
{ "type": "text", "text": "string" }
```

**image** — full-width image, 16:10 aspect ratio, rounded corners. If no url,
render an empty placeholder box (do not fetch anything from the network).
```json
{ "type": "image", "url": "string (optional, local file path or empty)" }
```

## Color handling — important implementation detail
When originally built in HTML, colors applied via CSS custom-property
inheritance (`--accent-c`) did NOT reliably cascade into `<table>` elements
across some rendering contexts. The fix was to compute and apply each color
as a **direct, explicit color value on each element** rather than relying on
inheritance. Recommend the same approach in Compose: pass the resolved
`Color` value directly down to each child composable (title text, table
header background, table stripe rows, numbered-list badges) rather than
relying on a single CompositionLocal that children might not consistently
read down through intermediate layout containers. Being explicit avoids a
class of subtle color bugs we hit repeatedly during the HTML prototype phase.

For the table row tint: blend the block's accentColor hex toward white by
~78% (linear RGB blend: `result = color + (255 - color) * 0.78` per channel)
rather than using alpha transparency over the page background — alpha
blending against a non-white background shifts hues (blue read as grey,
green read as khaki) which was a real bug found during design review.

## Visual design tokens (from the HTML prototype)
- Background: `#F6F1E8` (warm cream)
- Card/raised surface: `#FFFFFF`
- Primary text: `#2B2620`
- Dim/secondary text: `#8A8175`
- Divider lines: `#E4DCCC`
- Default accent (fallback if none specified): `#A6543C`
- Card title: serif font (Georgia or similar), ~27sp, centered, colored with
  the resolved accent
- Body/list text: system sans-serif, ~16-17sp
- Section/table headings: ~12sp, uppercase-free, colored with accent, with a
  bottom divider line
- Numbered list badges: small filled circles in the block's accent color,
  white number text
- Table header row: solid accent color background, white text
- Corner radius: ~10px on tiles, tables, image placeholders (not overused
  elsewhere)

## Explicitly out of scope for this version
- No folders/categories, no multiple saved decks list — one file loaded at a
  time
- No in-app card editor — decks are authored externally (in chat) and loaded
  as-is
- No AI/API calls from within the app
- No login or cloud sync — everything is local to the device for this version
- No image loading from URLs — if an image block has no local content, show
  a placeholder only

A working Android app (Kotlin, Jetpack Compose) with the two screens above,
